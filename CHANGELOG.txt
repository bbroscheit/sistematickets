2026-09-15 (fix crítico: no existía migración para el modelo Role)
-------------------------------------------------------------------
- El usuario preguntó si ya estaba todo listo para hacer commit/push y
  después asignar roles en producción. Antes de confirmar, se revisó
  qué migraciones existen (api/migrations/) contra lo que el código
  realmente necesita, y apareció un problema serio: el modelo Role
  (api/src/models/role.js) y la columna users.roleId (inferida por la
  asociación `User.belongsTo(Role, {as:'role'})` en bd.js) NUNCA
  tuvieron una migración - ni una. En local funcionaba solo porque la
  base de datos local se reconstruyó a mano esta sesión (por eso
  "roles" y "roleId" ya existían ahí sin que ninguna migración los
  haya creado).
- Por qué esto rompía el plan "commit + push + asignar roles": en
  producción la tabla "users" YA EXISTE de antes. api/index.js corre
  `conn.sync({force:false})` en cada arranque, que SOLO crea tablas
  que faltan - nunca agrega columnas nuevas a una tabla que ya existe.
  O sea: al desplegar este código en producción, sync() iba a crear la
  tabla "roles" (vacía, sin los 4 roles) pero NO iba a poder agregar
  "roleId" a "users" - cualquier consulta que incluya el rol de un
  usuario iba a tirar un error real de SQL ("column does not exist"),
  no el error ya resuelto de "usuario sin rol asignado".
- Se creó api/migrations/20260915000000-add-roles-table-and-userid.js:
  crea la tabla "roles", carga los 4 roles (empleado/encargado/
  jefe/gerente, mismos niveles que en local) y agrega la columna
  users.roleId (nullable, FK a roles, ON DELETE SET NULL). Es
  defensiva a propósito: chequea si la tabla/columna/filas ya existen
  antes de crearlas, por si sync() ya alcanzó a crear la tabla "roles"
  vacía en algún arranque previo con este código ya en producción.
  Probada corriendo migration.up() directo contra la base local (que
  ya tiene todo esto creado a mano): no rompe nada, detecta que ya
  existe y no hace nada.
- Sigue pendiente confirmar con el usuario si alguna de las otras 2
  migraciones nuevas (managerId, sector Mesa de Ayuda) ya se corrió
  alguna vez contra producción, y cuál es el proceso real de deploy
  (¿se reinicia el server antes o después de correr las migraciones?)
  antes de dar por seguro el orden commit -> push -> migrar -> asignar
  roles.

2026-09-14 (fix: "Crear Proyecto" no hacía nada al apretarlo)
-------------------------------------------------------------------
- Reportado por el usuario: al apretar "Crear Proyecto" no pasaba
  absolutamente nada (ni error ni éxito). Reproducido con curl
  simulando el mismo POST multipart que manda el formulario.
- Causa real (backend, preexistente - no introducida por el V2):
  api/src/routes/controllers/postNewProject.js hace
  `fs.mkdirSync(folderPath)` SIN `{recursive: true}` para crear la
  carpeta del proyecto dentro de client/public/Proyectos/ - pero esa
  carpeta "Proyectos" nunca existió en este entorno. mkdirSync tira
  ENOENT porque no puede crear una carpeta si el padre tampoco existe,
  eso se cae en el catch de la función (que solo hace console.log) y
  la función devuelve undefined -> la ruta responde 400 "failure" ->
  el frontend, que solo manejaba el caso "success", no mostraba nada.
  Fix: se agregó `{recursive: true}`.
- Efecto secundario del mismo bug: como `Newproject.create()` corre
  ANTES del mkdirSync que fallaba, cada intento fallido igual dejaba
  una fila húerfana en la base (sin carpeta ni archivos). Se
  encontraron 2 filas así ("prueba de desarrollo", ids 1 y 2) que
  parecen ser intentos previos del usuario - se dejaron sin tocar,
  pendiente de confirmar si se pueden borrar.
- nuevoProyectoV2.js: se agregó manejo real de error (Swal de error)
  para el caso en que postProject no devuelva "success" o falle la
  petición - antes ese caso no mostraba nada, igual que en la ruta
  original nuevoProyecto.js (no se tocó esa, sigue con el mismo bug de
  no avisar en error, más allá de que ahora sí va a funcionar el alta).
- Se encontró el mismo patrón (mkdirSync sin recursive) en
  updateNewProject.js (se usa al editar un proyecto y subir archivos
  desde proyectos/[id].js) - mismo riesgo en producción apenas alguien
  suba el primer archivo ahí. Se aplicó el mismo fix. postTicket.js y
  postTicketAndDesarrollo.js tienen el mismo mkdirSync sin recursive
  pero apuntan directo a client/public (carpeta que sí está en el
  repo), no a una subcarpeta que no existe - no corren el mismo riesgo,
  no se tocaron.

2026-09-09 (fix: la restauración de la URL no se aplicaba)
-------------------------------------------------------------
- La URL guardaba bien ?view=1&worker=1, pero al volver la pantalla
  igual mostraba "Todos". Causa: la restauración vivía adentro de
  applyData(), llamada desde el useEffect de carga (dependencias []) -
  ese efecto corre una sola vez al montar, y en ese momento
  router.query puede todavía estar vacío (router.isReady en false, un
  tick de Next.js) incluso viniendo de un "atrás" del navegador. Como
  ya se había marcado "restaurado" con esa primera lectura vacía, nunca
  se volvía a intentar aunque el query apareciera un instante después.
- Fix en NewTicketSupervisorV2.js y NewTicketSupervisorGeneralV2.js:
  se separó la restauración a su propio useEffect, con
  [router.isReady, router.query, worker/usuarios] como dependencias -
  así se aplica en el momento en que router.isReady sea true Y los
  datos ya hayan llegado, sea cual sea el que tarde más.
